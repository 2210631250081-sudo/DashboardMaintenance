# SAP PM Dashboard: frontend demo (standalone)

Plain HTML, CSS and JavaScript. **Not integrated with B2E**, SAP or Call System. It exists to be studied and discussed with IT before being adapted to B2E.

| Module | Data source |
|---|---|
| 01 Reliability & Cost | `CALL SISTEM 2026.xlsx`, sheet `new section` (Oct 2025 to Apr 2026) |
| 02 Maintenance Calendar | Google Sheet `Data_dashboard`, tab `Maintenance_Kalender` (read live, see "Google Sheets connection"). The copy in `js/data.js` comes from `Data_dashboard.xlsx` (719 orders: 699 for plant 6410 and 20 for plant 6420, May to Oct 2026, updated 3 Nov 2026; the sheet also has a `Description` column (SAP `CAUFVD-KTEXT`) and, since 17 Nov 2026, three dummy columns to the right of Plant: `Finish`, `Range`, `Status`, with no SAP field chosen yet) |
| 03 Inventory Monitoring | Google Sheet `Data_dashboard`, tab `Min_Max_Stok` (read live). The copy in `js/data.js` comes from `Data_dashboard.xlsx` (16127 rows: 7899 for plant 6410 and 8228 for plant 6420, updated 3 Nov 2026) |
| 04 Request PR | Materials from the Inventory data (`Min_Max_Stok`), machine numbers from the Maintenance Calendar data (last 5 characters of `Equipment_No`). Requests are saved in the browser (localStorage), see "Request PR (menu 04)" |

## Run locally
1. Unzip and open `index.html` in a browser (no server, build step or install needed).
2. Internet is needed for two things: Chart.js 2.4.0 from cdnjs, and reading the Google Sheet (without internet the page shows the copy in `js/data.js` and says so in the bar under the title).
   Chart.js: For offline use, download that file, save it as `vendor/Chart.min.js`, and change the script tag in `index.html` to `vendor/Chart.min.js`. Without Chart.js, the KPIs, calendar and tables still work and a warning banner appears.
3. Optional data and calculation checks (Node.js): `node test/validate.js`

## Google Sheets connection (Maintenance Calendar and Inventory Monitoring)
The page reads the two tabs straight from the Google Sheet when it opens, every 5 minutes after that, and when the refresh button (red, top right of the bar) is pressed. A change made in the sheet therefore shows up within a few minutes, without touching any file. It is "near real time", not instant: Google can hold a change back for a short while.

- **Sheet link and tab names** are at the top of `js/sheets.js` (`sheetId`, `orders.sheet`, `materials.sheet`, `refreshMinutes`).
- **Sharing**: the spreadsheet must be shared as "Anyone with the link: Viewer", otherwise Google answers with a sign-in page and the dashboard falls back to `js/data.js`. Anyone with the link can read the sheet, so only dummy or non-confidential data belongs there.
- **Layout the page expects** (same as `Data_dashboard.xlsx`): column A is a marker (`Value` on data rows; rows with other text in column A, such as SAP / Dashboard / Table Name / FieldName, are label rows and are ignored). Columns are found by their title row: `Order, Equipment_No, Type_Order, Description, Planned_Start, Plant` (optional, right of Plant: `Finish, Range, Status`; if they are missing the page still works and shows `-`) and `Plant, Material, Description, Minimum Stock, Maximum Stock, Actual Stock`. If the title row cannot be found, the same columns are read by position (B to G) and the bar says "columns read by position". Do not insert, delete or reorder columns without telling the dashboard owner.
- **Values**: `Planned_Start` as `31/7/2026` or `2026-07-31`; stock columns as plain numbers. Empty `Minimum Stock` and `Maximum Stock`, or 0, mean "not set". Rows with an invalid value (text in a number column, impossible date, empty Plant / Material / Order / Actual Stock) are ignored and counted in the bar, which then turns orange.
- **If the sheet cannot be read** (no internet, not shared, wrong tab name, browser blocks it), nothing breaks: the page keeps the data it already has (the `js/data.js` copy, or the last good read) and the bar says what went wrong.
- **How the tabs are requested**: by tab name through Google's "gviz" address, loaded as a `<script>` tag. A plain `fetch()` to that address is blocked by the browser (CORS error, seen when `index.html` is opened from a folder), a script tag is not. The two tabs are requested one after the other.
- **Alternative**: File > Share > Publish to web, choose the tab and "Comma-separated values (.csv)", and paste each link into `csvUrl` in `js/sheets.js` (one per tab). Those links are read with `fetch()`, which Google allows for published CSV. No other change is needed.
- **In B2E** this must not stay: the data comes from the C# backend. Replace `js/sheets.js` with the backend call (`_fw_post`) that returns the same two lists (orders, materials); `calc.js` and `ui.js` do not need to change.

## Update the fallback copy and Reliability data
`js/data.js` is still read for Reliability & Cost (`var REL`, from `CALL SISTEM 2026.xlsx`) and is the fallback for the other two modules. To refresh the fallback after the Google Sheet changes, regenerate the matching block in `js/data.js` (`var MAT` for tab `Min_Max_Stok`, `var ORD` for tab `Maintenance_Kalender`), then run `node test/validate.js`. If the counts change, update the expected numbers in `test/validate.js` as well.

## Rules used
- Reliability (KALKULASI slide): IR (%) = Breakdown Time / Loading Time x 100; MTTR = Breakdown Time / Breakdown Frequency; MTBF = Loading Time / Breakdown Frequency. Loading Time = working hours - planned stop. Times are in minutes in the source and shown in hours. For a period, times and frequencies are summed first, then divided.
- Loading Time, Breakdown Time and Breakdown Frequency (troubles with Mesin Stop = Yes) are the per-section monthly figures in sheet `new section`. With these figures the formulas reproduce the IR, MTTR and MTBF printed in that sheet (checked in `test/validate.js`). PROD 1 to 3 = Cikarang, PROD 4 and 5 = Karawang.
- Maintenance cost, per-machine Loading Time and May 2026 are not available in the Call System file, so they show Unavailable or are left out.
- Calendar: each order is shown on its planned start date, shown as one count per day (all orders are preventive maintenance, so there is no order-type colour, legend or Category filter). Top of the page: four tiles. Planned Maintenance = orders whose planned start falls in the shown month (after the filters); Completed (Actual) = those with Status `Complete`; Overdue / Not Completed = those with Status `Overdue / Not Complete`; Plan Attainment = Completed / Planned (shown with the ratio). The three Status tiles show Unavailable while no order of the month has a Status value.
- Calendar toolbar (above the calendar): previous month and next month icons, a Month dropdown (April to March) and a Year dropdown in fiscal years. Fiscal year = April to March, named by the year it ends: 2026FY = April 2025 to March 2026 (the May to October 2026 data is 2027FY). Choosing a month or year moves the calendar, tiles, lists and table to that month.
- Calendar tables (the list under the calendar and the "Maintenance orders" table) have 8 columns: **Plant** (6410 = Cikarang, 6420 = Karawang), **Order**, **No. Mesin** (last 5 characters of Equipment_No, e.g. 64PM00074026 gives 74026), **Description**, **Range** (A, B, C or D), **Planned Start**, **Finish**, **Status**. The order type (ZPM1 / ZPM2) is not shown anywhere any more; the Type_Order column stays in the sheet and in the data.
- Calendar filters (left panel; applied to the calendar, the lists, the tiles, the chart and the table): **Search** (order, equipment or description), **Plant**, **Status** (Complete / Overdue / Not Complete). FILTER DATA redraws, and the dropdowns also react as soon as they change.
- Status is typed in the sheet, not calculated by the dashboard. Accepted spellings: `Complete` / `Completed`, and `Overdue`, `Not Complete(d)` or `Overdue / Not Complete`. Anything else counts as no Status.
- Inventory: Gap = Actual Stock - Minimum Stock, calculated by the app (Unavailable when no minimum is set). Two separate columns. **Category**: Slow Moving when Minimum and Maximum are both 0 or empty (not maintained in SAP), Fast Moving when a Minimum and/or Maximum is set. **Status**, first match wins: Out of Stock when Actual Stock is 0 (any category); Below Minimum (only when a Minimum is set); Above Maximum (only when a Maximum is set); Normal (there is no Unclassified status any more: a material with a Maximum but no Minimum is Above Maximum or Normal) (a Slow Moving material with stock has no Minimum or Maximum to cross, so it is Normal). Plant is shown as Cikarang (6410) or Karawang (6420). The sheet has no unit column, so quantities are shown without a unit. The inventory table shows 200 rows at a time (button "Show more"); the count and KPIs always cover all rows that match the filters.

## Request PR (menu 04)
Added 18 Nov 2026. Technicians ask for material; the admin makes the PR in SAP from those requests. The other three modules were not changed: the only edits outside the new files are the menu button, the section and the script tag in `index.html`, two lines in `js/ui.js` (the tab list and the refresh hook) and a CSS block at the end of `css/styles.css` (all selectors start with `#tab-rp` or `.rp-`).

- **Form**: Plant (Cikarang, Karawang); Material and Nomor Mesin (type to search, the list shows code and description / machine number and plant, at most 50 rows); Status Mesin (RUN, STOP, TPM); Pemakaian Untuk Tanggal (calendar, opens on the current month); Satuan (EA, PCS, KG); Quantity (digits only, whole number above 0); Status (URGENT, STOCK, MAINT; URGENT is preselected as in the reference screen); Keterangan. The Material and Nomor Mesin lists follow the chosen Plant.
- **NON MASTER / SV**: always the first two entries of the Material list. After choosing one, a text box asks for the material description (max 40 characters, the SAP short text length; whatever was typed in Material is copied into it). Without master data the stock boxes show 0.
- **Stock boxes**: Stok Cikarang and Stok Karawang = Actual Stock of the material in plant 6410 / 6420; Standar Stok = Minimum – Maximum Stock of the chosen plant. The Aging box of the reference screen was left out.
- **Table**: columns as in the reference screen (TANGGAL, NAME, MATERIAL, DESCRIPTION, MAKER, QTY, STATUS, PLANT, NO MESIN, STATUS MESIN, NO PR, TANGGAL PR), newest first, a filter box under each header, and Tanggal Dari / Tanggal Sampai (default: yesterday and today; "Kosongkan" in the calendar removes a limit). Satuan, Pemakaian Untuk Tanggal and Keterangan are in the tooltip of the QTY cell. MAKER stays empty (no source). The admin types NO PR and TANGGAL PR in the row; a row with a NO PR fades and cannot be deleted. Delete asks for a second click.
- **Excel to SAP** (`REQUEST PR - <date>.xlsx`): every request without a NO PR, oldest first, whatever the date filter says. Columns: JML CHAR, REQUESTOR (see below), PLANT, MAPIN, PURCH GROUP, MATERIAL GROUP, MATERIAL, MATERIAL DESCRIPTION, QTY, UNIT, PRICE, (empty column), DELIVERY DATE, TRACKING NUMBER, KETERANGAN. PLANT 6410 / 6420 with PURCH GROUP 64G / 64H; MAPIN 6400 for both plants (6420 not confirmed); DELIVERY DATE = Pemakaian Untuk Tanggal; TRACKING NUMBER = machine number + Status (e.g. `33002STOCK`); JML CHAR, MATERIAL GROUP and PRICE stay empty (filled by hand in SAP). MATERIAL DESCRIPTION is filled only for NON MASTER and SV; for NON MASTER and SV the MATERIAL column holds the words `NON MASTER` / `SV`.
- **REQUESTOR** = requester + first letter of the machine status + first letter of whoever downloads Excel to SAP, in capitals. Example: Fajar requests, the machine is STOP, admin Parmi downloads -> `FAJAR-S-P` (a RUN machine gives `FAJAR-R-P`, TPM gives `FAJAR-T-P`). It is worked out when the file is made, so the same request gets a different last letter when another admin downloads. The NAME column of the table and of Export Excel is the user who filled the request.
- **User login (demo)**: the box at the top of the page stands in for the login, so one browser can play both roles (choose Fajar, add a request; choose Parmi, press Excel to SAP). The users are listed in `CFG.users` (`name` = NAME column, `code` = short user name used in REQUESTOR). Delete the box when B2E provides the logged-in user.
- **Export Excel** (`REQUEST PR.xlsx`): the rows shown in the table (date filter and header filters), newest first, with the title rows `Request PR | CMMS` and `REQUEST PR`, filter arrows on the header and dates as dd/mm/yyyy.
- **Settings** are at the top of `js/request-pr.js` (`CFG`): the demo users (`users`), which Status field gives the middle letter of REQUESTOR (`requestorStatus`), plant names / purchasing group / MAPIN, the option lists, the 40 character limit.
- **Data**: requests are kept in `localStorage` key `cmms_request_pr_v1` of the browser, so they are not shared between computers. On the first start 18 sample rows copied from the reference screenshots are created (the ones of yesterday already have a dummy PR number `DEMO-xxxx`). To start empty again, delete that key in the browser (F12, Application, Local Storage). In CMMS / B2E the requests must come from the backend (C# by IT) and NAME and the requester / downloader part of REQUESTOR from the logged-in user.
- **Not verified**: the page and both Excel files were checked in headless Chromium and by reading the files back with openpyxl and LibreOffice, not in Microsoft Excel or SAP. The middle letter of REQUESTOR (taken from the machine status as described; the reference SAP file shows `BUDIL-S-P` for rows whose machine status is RUN, which would fit the Status field STOCK instead, switch with `CFG.requestorStatus`), MAPIN for Karawang and the content of MATERIAL for NON MASTER / SV are assumptions to confirm. The machine list only has machines that appear in the Maintenance Calendar data (305 machines).
